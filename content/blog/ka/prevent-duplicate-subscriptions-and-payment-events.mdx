<p><strong>მოკლე პასუხი:</strong> ერთი payment intent-ის ხელახლა გაგზავნა უნდა დაბრუნდეს იმავე შედეგში და არ შექმნას ახალი charge, subscription ან access transition. ამისთვის intent-ს მიაბით სტაბილური idempotency key, provider event ერთხელ შეინახეთ, database-ში uniqueness დაამყარეთ და side effect-ები durable transition-ს დაუკავშირეთ. <a href="/ka/contact">მოითხოვეთ არსებული AI-ით შექმნილი აპის scoped review</a>, თუ ამ ჯაჭვის მტკიცებულება არ გაქვთ.</p>

<h2 id="rule">დუბლირებული payment action-ის მთავარი წესი</h2>

<p>დუბლირება ჩნდება მაშინ, როცა ერთი ბიზნეს-განზრახვა სისტემას ორჯერ აღწევს ან ერთი შედეგი ორ სხვადასხვა გზაზე იქმნება. მომხმარებელმა შეიძლება ღილაკს ორჯერ დააჭიროს, ქსელის პასუხი დაიკარგოს, worker-მა retry გააკეთოს, provider webhook-ი ხელახლა გამოაგზავნოს ან ორი პროცესი ერთ subscription-ზე ერთდროულად იმუშაოს.</p>

<p>Idempotency ნიშნავს, რომ ერთი და იგივე განზრახვის გამეორება იმავე ბიზნეს-შედეგს აბრუნებს. ეს არ არის მხოლოდ provider პარამეტრი. კონტროლი საჭიროა browser-to-server request-ზე, server-to-provider call-ზე, webhook endpoint-ზე, webhook worker-ზე და entitlement ledger-ზე. თითოეულ საზღვარს თავისი key, durable record და retry წესი უნდა ჰქონდეს.</p>

<p><a href="https://docs.stripe.com/api/idempotent_requests">Stripe idempotent requests დოკუმენტაცია</a> ამბობს, რომ იგივე key-ით განმეორებითი request პირველივე შედეგის status code-სა და body-ს აბრუნებს, მათ შორის 500 შეცდომასაც. ეს ამცირებს გაურკვევლობას provider call-ის დროს, მაგრამ არ ასრულებს თქვენი აპის database update-ს, email-ს ან access transition-ს. თქვენი სისტემა კვლავ უნდა იცავდეს საკუთარ side effect-ებს.</p>

<h2 id="retry-path">ერთი intent, ორი retry: სად იბადება დუბლირება?</h2>

<p>ვივარაუდოთ, რომ მომხმარებელი subscription start-ს ითხოვს. server provider-ს request-ს უგზავნის, მაგრამ პასუხამდე connection წყდება. მომხმარებელს ეჩვენება, რომ გადახდა ვერ დასრულდა და ისევ აჭერს ღილაკს. თუ მეორე request-ს ახალი key აქვს, provider-ს შეიძლება ორი დამოუკიდებელი ოპერაცია მიუვიდეს. თუ ერთი key გამოიყენეთ სხვა პარამეტრებთან ერთად, provider წესი უნდა დაგიბრუნოთ კონფლიქტს და თქვენ უნდა შეაჩეროთ გაურკვეველი განმეორება.</p>

<p>კიდევ ერთი გზა webhook-ია. Provider-მა შეიძლება მოვლენა თავიდან მიაწოდოს, რადგან endpoint-ის პასუხი ვერ დაინახა. Event-ის მეორედ მიღება არ ნიშნავს, რომ invoice ან access მეორედ უნდა შეიქმნას. ჩაიწერეთ provider event ID, შეამოწმეთ ხელმოწერა, შეეცადეთ ერთხელ ჩასვათ event ledger-ში და მხოლოდ ახალი ჩანაწერის შემთხვევაში გაუშვით state transition.</p>

<p><a href="https://docs.stripe.com/webhooks">Stripe webhook guide</a> ამოწმებს ხელმოწერისა და endpoint-ის დამუშავების წესს, თუმცა provider-ის ოფიციალური delivery ვერ ცვლის თქვენს local ledger-ს. Event source-ის დადასტურება და იგივე event-ის მეორედ დამუშავების შეჩერება ორი ცალკე მტკიცებულებაა.</p>

<p><a href="/ka/blog/webhookis-khelmotseris-shemotsmeba-aiit-shekmnil-apshi">webhook ხელმოწერის შემოწმება</a> ცალკე კონტროლია: ხელმოწერის სწორი შედეგი ადასტურებს წყაროს, მაგრამ არ გამორიცხავს იმავე სანდო event-ის განმეორებით მიწოდებას. ამიტომ authenticity და deduplication ერთი და იგივე შემოწმებად არ ჩათვალოთ.</p>

<h2 id="key-lifecycle">idempotency key lifecycle და მონაცემის შენახვა</h2>

<p>Key უნდა წარმოადგენდეს კონკრეტულ intent-ს და არა უბრალოდ მომხმარებელს. `start-subscription:user-123` შეიძლება ზედმეტად ხანგრძლივი ან ორაზროვანი იყოს; უფრო სასარგებლოა server მიერ შექმნილი შემთხვევითი key, რომელიც ერთ checkout attempt-ს ეკუთვნის. Stripe მითითებით key სიგრძე მაქსიმუმ <strong>255</strong> სიმბოლოა და გასუფთავება შეიძლება მოხდეს მაშინ, როცა key მინიმუმ <strong>24</strong> საათისაა. ეს provider წესი არის, არა თქვენი პროდუქტის სრული retention პოლიტიკა.</p>

<p>თქვენს ledger-ში შეინახეთ key, operation type, account ან customer reference, provider object ID, request fingerprint, processing state, created time და საბოლოო result reference. თუ იგივე key სხვა თანხით ან სხვა subscription-ით დაბრუნდა, ხელახლა execution არ დაიწყოთ. დააბრუნეთ მკაფიო conflict და დატოვეთ შემოწმებადი ჩანაწერი.</p>

<p>Side effect-ები ცალკე უნდა დაიცვათ. Database transition-ის შემდეგ email, credit, invoice note ან analytics event worker-ში გადაიტანეთ და მათაც მიეცით deduplication key. თუ email commit-მდე გაიგზავნა, event row-ის უნიკალურობა ვერ დაიცავს მომხმარებელს ორი შეტყობინებისგან.</p>

<h2 id="faq">ხშირად დასმული კითხვები</h2>

<h3 id="faq-1">იგივე idempotency key უნდა გამოვიყენო ყველა მომხმარებლისთვის?</h3>
<p>არა. key კონკრეტულ ბიზნეს-განზრახვას უნდა ეკუთვნოდეს. იგივე key reuse სხვა მომხმარებლის, სხვა თანხის ან სხვა ოპერაციისთვის კონფლიქტსა და გაურკვეველ შედეგს ქმნის.</p>

<h3 id="faq-2">უნიკალური event row საკმარისია duplicate email-ის ასარიდებლად?</h3>
<p>არა. event row უნიკალურობა მხოლოდ მიღებული event გამეორებას აკონტროლებს. email ან credit worker-ს საკუთარი durable transition reference და deduplication წესი სჭირდება.</p>

<h3 id="faq-3">რა გავაკეთო, თუ provider და local subscription ერთმანეთს არ ემთხვევა?</h3>
<p>არ შეცვალოთ access მხოლოდ ბოლო webhook-ის მიხედვით. შეადარეთ provider object, ხელმოწერით დადასტურებული event history და local ledger, შემდეგ reconciliation-ის შედეგი ადამიანურ owner-ს გადასცით.</p>

<h3 id="faq-4">როგორ შევამოწმო duplicate billing live charge-ის გარეშე?</h3>
<p>გამოიყენეთ provider sandbox და დამტკიცებული test objects. გაიმეორეთ ერთი request key, იგივე event ორჯერ მიაწოდეთ და ორი worker გაუშვით, შემდეგ კი გადაამოწმეთ ერთი transition და side effect-ების ერთი ნაკრები.</p>
