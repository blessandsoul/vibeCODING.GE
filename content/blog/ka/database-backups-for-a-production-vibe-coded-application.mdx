<h2 id="what-ready-means">რას ნიშნავს backup და restore მზადყოფნა</h2>

<p>წარმოიდგინეთ ონლაინ სერვისი, რომელსაც აქვს მომხმარებლები, ავტორიზაცია, შეკვეთები, ატვირთული ფაილები და გარე გადახდის პროვაიდერი. მხოლოდ database-ის ასლი ამ სისტემის სრული აღდგენა არ არის. საჭიროა გაირკვეს, სად ცხოვრობს თითოეული stateful ნაწილი, რომელი წყაროა საბოლოო და რა შეიძლება ხელახლა შეიქმნას.</p>

<p>კარგი მიზანი წერია ბიზნესის ენაზე: რომელი პროცესი უნდა დაბრუნდეს პირველ რიგში, რამდენი დროის მიუღებელი პაუზა არსებობს და რამდენი ბოლო ცვლილების დაკარგვაა მისაღები. ტექნიკურ გეგმაში ამ კითხვებს RTO და RPO ეწოდება. მნიშვნელობა თვითონ აბრევიატურას არ აქვს; მნიშვნელობა აქვს შეთანხმებულ ზღვარს და შემოწმების ჩანაწერს.</p>

<p><a href="https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_backing_up_data_periodic_recovery_testing_data.html">AWS Well-Architected-ის recovery guidance</a> პირდაპირ აკავშირებს restore ტესტს მონაცემის მთლიანობასთან, RTO-სთან და RPO-სთან. გვერდი აფრთხილებს, რომ backup-ის არსებობის ვარაუდი ან restore-ის შემდეგ მონაცემის წაუკითხავად დატოვება recovery-ის მტკიცებულება ვერ იქნება.</p>

<h2 id="comparison">backup მიდგომების შედარება</h2>

<p>PostgreSQL <strong>18</strong>-ის <a href="https://www.postgresql.org/docs/18/backup.html">ოფიციალური დოკუმენტაცია</a> ერთმანეთისგან განასხვავებს SQL dump-ს, file-system backup-ს და continuous archiving-ს. ეს განსხვავება პრაქტიკულია: არჩეული მეთოდი უნდა შეესაბამებოდეს თქვენს მონაცემთა ბაზას, ხელმისაწვდომ ფანჯარას და აღდგენის ამოცანას. ნუ ჩათვლით provider-ის სიტყვას „backup“ აპლიკაციის სრულ სურათად.</p>

<h2 id="restore-drill">როგორ ჩაატაროთ უსაფრთხო restore drill</h2>

<p>Restore უნდა ჩატარდეს ისეთ გარემოში, რომელიც production-ის მომხმარებლებს არ ეხება. მიზანია პროცედურის შემოწმება და არა ცოცხალ მონაცემებზე ექსპერიმენტი. გამოიყენეთ ეს თანმიმდევრობა:</p>

<ol>
  <li><strong>დააფიქსირეთ საზღვრები.</strong> მიუთითეთ რომელი backup აირჩევა, რა დროის მონაცემი უნდა დაბრუნდეს და ვინ აჩერებს ტესტს შეცდომისას.</li>
  <li><strong>გამოაცალკევეთ გარემო.</strong> შექმენით ახალი რესურსი ან იზოლირებული namespace. არ მიაბათ აღდგენილი აპლიკაცია ნამდვილ email, payment ან webhook endpoint-ს.</li>
  <li><strong>აღადგინეთ ტექნიკური დამოკიდებულებები.</strong> დააყენეთ schema, migration, ფაილების საცავი და მინიმალური configuration. საიდუმლო მნიშვნელობები ტესტის ჩანაწერში არ ჩაწეროთ.</li>
  <li><strong>შეამოწმეთ ბიზნესის ჩანაწერი.</strong> წაიკითხეთ ბოლო ცნობილი შეკვეთა, მომხმარებელი, ფაილის metadata და სხვა კრიტიკული ობიექტი. ცარიელი dashboard ვერ ადასტურებს წარმატებას.</li>
  <li><strong>გაიარეთ მნიშვნელოვანი journey.</strong> შემოწმდეს ავტორიზაცია, ჩანაწერის ნახვა, უსაფრთხო ცვლილება და საჭირო გარე ინტეგრაციის mock ან sandbox ქცევა.</li>
  <li><strong>შეადარეთ დრო და დანაკარგი.</strong> ჩაწერეთ restore-ის დაწყება, usable state-მდე მისვლა, დაკარგული ბოლო ცვლილება და იმ ზღვართან შედარება, რომელიც ბიზნესმა წინასწარ დაადგინა.</li>
  <li><strong>დააფიქსირეთ შედეგი.</strong> შეინახეთ არჩეული backup, გარემოს საზღვარი, შემოწმებული ჩანაწერები, შეცდომები, owner და შემდეგი repair. PASS მხოლოდ მაშინ დაწერეთ, როცა კრიტიკული კითხვა პასუხგაცემულია.</li>
</ol>

<p>Microsoft-ის <a href="https://learn.microsoft.com/en-us/azure/backup/backup-overview">Azure Backup overview</a> აჩვენებს policy-driven workflow-ს, recovery point-ს და სხვადასხვა დონის restore-ს. ეს დოკუმენტაცია კონკრეტულ Azure სერვისზეა; იგი არ ამტკიცებს თქვენი აპლიკაციის აღდგენადობას. სერვისის ფუნქცია და თქვენი პროცედურის ფაქტობრივი შედეგი სხვადასხვა მტკიცებულებაა.</p>

<p>სასწავლო ჩანაწერში HTTP <code>200</code> შეიძლება ნიშნავდეს მოსალოდნელ პასუხს, ხოლო <code>403</code> უარყოფილ წვდომას. დაკარგული კრიტიკული ჩანაწერების რაოდენობა ცალკე ჩაწერეთ და ნულოვანი შედეგი მხოლოდ მაშინ მიუთითეთ, როცა შესაბამისი შემოწმება ნამდვილად ჩატარდა. ეს რიცხვები ამ სტატიის მაგალითებია და არა თქვენი აპლიკაციის შედეგი.</p>

<h2 id="evidence">რა მტკიცებულება უნდა მიიღოს მფლობელმა</h2>

<p>საბოლოო პაკეტში სასარგებლოა ოთხი ცალკე ჩანაწერი: მონაცემთა რუკა, restore runbook, ტესტის ჟურნალი და ღია საკითხების სია. თითოეული ჩანაწერი უნდა მიუთითებდეს თარიღს, გარემოს, პასუხისმგებელ ადამიანს და იმ ნაწილს, რომელიც არ შემოწმებულა.</p>

<p>თუ ტესტმა მხოლოდ database-ის წაკითხვა დაადასტურა, დასკვნა უნდა იყოს „database წაკითხვადია იზოლირებულ გარემოში“. დასკვნა „აპლიკაცია აღდგა“ ზედმეტად ფართოა, თუ ფაილები, authentication, queue და გარე ინტეგრაციები არ შემოწმებულა. მსგავსი ზუსტი ენა გადაწყვეტილებას ამარტივებს და გადაჭარბებულ დაპირებას არ ქმნის.</p>

<h2 id="vibecoding-scope">რას ამოწმებს vibeCODING</h2>

<p>vibeCODING განიხილავს უკვე არსებულ AI-ით შექმნილ აპებს და ეხმარება მფლობელს security და production-readiness საკითხების დალაგებაში. საჯარო scan ამოწმებს იმას, რასაც ჩვეულებრივი visitor ჩამოტვირთავს. backup-ის private console, database ან restore გარემო საჯარო ფაილიდან არ დასტურდება.</p>

<p>უფრო ღრმა review, repair ან rescan მხოლოდ მაშინ შედის, როცა მფლობელი და review გუნდი წვდომასა და ტესტის საზღვრებს წინასწარ ათანხმებენ. ანგარიში აღწერს შემოწმებულ ზედაპირს, აღმოჩენას, შესაძლო გავლენას, repair-ის scope-ს და ხელახალი შემოწმების პირობას. ეს არ არის ახალი აპის აშენება, restore-ის გარანტია ან კონკრეტული provider-ის სერტიფიკატი.</p>

<p>ოპერაციული გადაბარება, monitoring და audit trail ცალკე საკითხებია; მათი შემოწმებისას იგივე წესი მოქმედებს: დაასახელეთ მტკიცებულება და დატოვეთ დაუდასტურებელი ნაწილი ღიად.</p>

<h2 id="faq">ხშირად დასმული კითხვები</h2>

<h3 id="faq-1">თუ backup job მწვანეა, საკმარისია?</h3>
<p>არა. უნდა დადასტურდეს აღდგენის ფაქტობრივი წაკითხვა, საჭირო მონაცემების არსებობა და შეთანხმებულ დროში დაბრუნება. მწვანე job მხოლოდ ერთი ტექნიკური სიგნალია.</p>

<h3 id="faq-2">შეიძლება restore პირდაპირ production-ში გავაკეთოთ?</h3>
<p>ეს სტატია ასეთ მოქმედებას არ გირჩევთ. ჯერ განსაზღვრეთ იზოლირებული ტესტი, stop პირობა და sandbox ინტეგრაციები. ცოცხალ მონაცემზე ნაბიჯი ცალკე ავტორიზაციას და მკაცრ runbook-ს მოითხოვს.</p>
