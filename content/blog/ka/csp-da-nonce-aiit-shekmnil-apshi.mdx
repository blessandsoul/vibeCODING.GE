<p><strong>პირდაპირი პასუხი:</strong> CSP არის ბრაუზერისთვის გაგზავნილი წესი, ხოლო nonce არის ერთ კონკრეტულ პასუხში დაშვებული სკრიპტის დამადასტურებელი შემთხვევითი მნიშვნელობა. მათი არსებობა მხოლოდ მაშინ არის სასარგებლო, როცა პასუხის header, nonce მნიშვნელობის ჩასმა და რეალურად გაშვებული სკრიპტები ერთმანეთს ემთხვევა. საჯარო აპის შემოწმება ამ თანხვედრას აჩვენებს, მაგრამ მთელ კოდს უსაფრთხოდ ვერ აცხადებს. თუ გჭირდებათ ასეთი შემოწმების საზღვრის განსაზღვრა, <a href="/contact">vibeCODING-ის scoped review მოთხოვნა გააგზავნეთ</a>.</p>

<h2 id="what-csp-does">CSP პოლიტიკის განმარტება</h2>
<p>Content Security Policy არის ბრაუზერის მიერ შესრულებული შეზღუდვების ნაკრები, რომელიც განსაზღვრავს, საიდან შეიძლება ჩაიტვირთოს სკრიპტი, სტილი, სურათი, frame ან სხვა რესურსი. <a href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP">MDN-ის განმარტებით</a>, პოლიტიკა შეიძლება მიეწოდოს HTTP header-ით ან შესაბამისი meta ელემენტით. ეს არის კლიენტის მიერ მიღებული წესის შესრულება და არა სერვერის ან ბიზნესის ყველა რისკის ავტომატური აუდიტი.</p>
<p>AI-ით აწყობილ აპში CSP ხშირად პირველად ჩნდება template-ში ან hosting-ის პარამეტრში. პრობლემა იწყება მაშინ, როცა header-ს ემატება ფართო გამონაკლისი, მაგალითად ყველა inline სკრიპტის დაშვება, ან როცა გვერდი იყენებს ისეთ რესურსს, რომელიც სიაში არ არის. უსაფრთხოების header-ების საერთო შემოწმება სასარგებლო საწყისი წერტილია, თუმცა nonce მნიშვნელობის რეალური კავშირი ცალკე უნდა დადასტურდეს.</p>

<h2 id="csp-vs-nonce">რა განსხვავებაა CSP-სა და nonce-ს შორის?</h2>
<p>CSP განსაზღვრავს პოლიტიკის ჩარჩოს, nonce კი ამ ჩარჩოში კონკრეტულ inline სკრიპტს ამოიცნობს. nonce არ არის მუდმივი პაროლი და არც მომხმარებლის იდენტიფიკაციის მექანიზმი. თუ ერთი მნიშვნელობა ყველა პასუხში მეორდება, ის აღარ ასრულებს იმ ფუნქციას, რომელსაც ერთჯერადი პასუხთან დაკავშირებული მნიშვნელობა უნდა ასრულებდეს.</p>

<h2 id="response-and-rendered-script">ბრაუზერის პასუხისა და გაშვებული სკრიპტის შემოწმება</h2>
<p>შემოწმება დაიწყეთ ერთი საჯარო URL-ით და ერთი კონკრეტული response-ით. შეინახეთ request-ის დრო, საბოლოო URL, status code და security header-ის ზუსტი მნიშვნელობა. შემდეგ DevTools-ში დააკვირდით რეალურ document-სა და script ელემენტებს. მხოლოდ hosting-ის dashboard-ში ნაჩვენები კონფიგურაცია საკმარისი მტკიცებულება არ არის.</p>
<ol>
  <li><strong>დააფიქსირეთ პოლიტიკა:</strong> ნახეთ, მოდის თუ არა Content-Security-Policy response-ში და აქვს თუ არა script-src მკაფიო წყაროები.</li>
  <li><strong>შეადარეთ მნიშვნელობა:</strong> nonce მნიშვნელობის ატრიბუტი კონკრეტულ inline სკრიპტზე უნდა ემთხვეოდეს იმავე პასუხის policy-ში დაშვებულ მნიშვნელობას.</li>
  <li><strong>იპოვეთ გამონაკლისები:</strong> შეამოწმეთ unsafe-inline, ზედმეტად ფართო წყაროები და ისეთი მესამე მხარის რესურსები, რომლებიც ბიზნესმა არ დაადასტურა.</li>
  <li><strong>გამოყავით უცნობი:</strong> თითოეული დაუდასტურებელი script, dynamic import და ჩატვირთვის გზა ცალკე ღია საკითხად ჩაწერეთ.</li>
</ol>
<p>Nonce-ის ტექსტი ანგარიშში სრულად არ ჩასვათ, თუ მას მოქმედი მნიშვნელობა აქვს. საკმარისია მიუთითოთ, რომ მნიშვნელობა პასუხზე იყო მიბმული და შესაბამისი script ატრიბუტი არსებობდა. <a href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/script-src">MDN-ის script-src reference</a> და Source map-ის ხილვადობის შემოწმება დაგეხმარებათ გაიმიჯნოს policy-ს დარღვევა და კლიენტში ზედმეტი build-ინფორმაციის გამჟღავნება.</p>

<h2 id="safe-rollout">CSP-ის უსაფრთხო rollout-ის გზა</h2>
<p>პოლიტიკის პირდაპირ გამკაცრება მოქმედ გვერდზე შეიძლება მოულოდნელად არღვევდეს გადახდას, ანალიტიკას, ავტორიზაციას ან სხვა აუცილებელ flow-ს. უსაფრთხო rollout იწყება იმით, რომ გუნდი ჯერ აღწერს საჭირო რესურსებს და მხოლოდ შემდეგ ამცირებს გამონაკლისებს. Report-only რეჟიმი შეიძლება დაკვირვებისთვის გამოდგეს, მაგრამ მისი ჩანაწერები მაინც უნდა გაარჩიოთ რეალურ დარღვევად და მოსალოდნელ ხმაურად.</p>
<p>თბილისის მცირე SaaS-ის გამოგონილ გუნდს შეიძლება ჰქონდეს ახალი landing page, რომელიც AI builder-მა ააწყო და ჯერ staging-ზე მუშაობს. თუ გუნდი production header-ს პირდაპირ გადაიტანს, ერთი analytics script შეიძლება დაიბლოკოს, ხოლო თვალით ყველაფერი ნორმალურად ჩანდეს. სწორი სამუშაოა staging-ის response-ის შენახვა, საჭირო წყაროების დამტკიცება, ერთი ცვლილების შეტანა და მთავარ user flow-ზე ხელახლა დაკვირვება. ეს სასწავლო სცენარია და aiNOW-ის კლიენტის რეალური შემთხვევა არ არის.</p>
<p>Staging-ის მომზადების სახელმძღვანელო გიჩვენებთ, რატომ უნდა გაიყოს ცვლილების ტესტი ცოცხალი მომხმარებლებისგან. CSP-ის მიზანი არ არის ყველა ბლოკის უხეშად აკრძალვა; მიზანია დამტკიცებული რესურსების მკაფიო საზღვარი, რომელსაც გუნდი შემდეგაც შეძლებს ახსნას.</p>

<h2 id="browser-and-owner-checks">რა უნდა შეამოწმოს გუნდმა ბრაუზერის გარეთ?</h2>
<p>Header-ის შემოწმება ვერ პასუხობს კითხვას, ვის აქვს აპის შეცვლის უფლება, როგორ ხდება build-ის გამოქვეყნება ან სად ინახება საიდუმლო მნიშვნელობები. ამიტომ ტექნიკური მიმოხილვის სამუშაო ფურცელში CSP-ს გვერდით ჩაწერეთ deployment-ის მიმოხილვა, წვდომის პასუხისმგებელი და ცვლილების დაბრუნების გზა.</p>
<p>თუ report-only შეტყობინება მიუთითებს უცნობ დომენზე, ჯერ არ ჩათვალოთ, რომ მისი დაშვება უსაფრთხოა. დაასახელეთ მფლობელი, მიზანი, მონაცემის ტიპი და აუცილებლობა. შემდეგ გადაწყვიტეთ, უნდა დაემატოს თუ არა წყარო, შეიცვალოს თუ არა ინტეგრაცია, ან ამოიღოს თუ არა კოდიდან. Production handover-ის ჩეკლისტი დაგეხმარებათ, ეს გადაწყვეტილებები მხოლოდ ერთ დეველოპერზე არ დარჩეს.</p>

<h2 id="review-sheet">საბოლოო სამუშაო ფურცელი CSP მიმოხილვისთვის</h2>
<p>პირველ სვეტში ჩაწერეთ გვერდის URL, response-ის დრო და მიღებული Content-Security-Policy header. მეორე სვეტი დაუთმეთ script-src წყაროებს, nonce მნიშვნელობის არსებობასა და report-only შეტყობინებებს. მესამე სვეტში ჩაწერეთ კოდის მფლობელი, ცვლილების ticket და შეთანხმებული შემდეგი ნაბიჯი. ასეთი ფურცელი ხელს უშლის ერთ დიდ დასკვნას, რომელიც ერთმანეთში ურევს browser policy-ს, deployment-სა და backend authorization-ს.</p>
<p>ყოველი აღმოჩენა აღწერეთ ოთხი მოკლე ველით: დაკვირვება, მტკიცებულება, შესაძლო გავლენა და დასადასტურებელი შემდეგი შემოწმება. მაგალითად, „inline script-ს აქვს nonce“ არის დაკვირვება; response header და HTML ატრიბუტი არის მტკიცებულება; policy-ს დარღვევის შემცირება არის შესაძლო გავლენა; cache-ისა და სხვა route-ის შემოწმება არის შემდეგი ნაბიჯი. სიტყვები „უსაფრთხოა“ და „დაცულია“ გამოიყენეთ მხოლოდ იმ scope-ში, რომელიც რეალურად შემოწმდა.</p>
<p>Release შეხვედრაზე ცალკე წაიკითხეთ სამი სია: დაშვებული რესურსები, დროებითი გამონაკლისები და უცნობი რესურსები. დროებით გამონაკლისს დაურთეთ მფლობელი, ვადა და დაბრუნების პირობა. უცნობი დომენი არ გადაიყვანოთ დაშვებულ სიაში მხოლოდ იმიტომ, რომ გვერდი მის გარეშე აღარ იტვირთება. ჯერ მოძებნეთ ინტეგრაციის მიზანი, მონაცემის ტიპი და ყველაზე მცირე საჭირო გზა. საბოლოო ჩანაწერი უნდა იძლეოდეს იგივე შემოწმების გამეორების შესაძლებლობას staging-ზე და შემდეგ production-ზე.</p>
<p>სარევიზიო ცხრილში დაამატეთ browser-ის ვერსია, საბოლოო URL, response header, HTML ფრაგმენტი, აღმოჩენილი წყარო და შემოწმების შედეგი. თითოეული ველი უნდა იკითხებოდეს მეორე ინჟინრისთვისაც. ცარიელი ველი აღნიშნავს უცნობ ფაქტს და არა ნეიტრალურ პასუხს. განსხვავებული route-ები ცალკე რიგებად ჩაწერეთ, რადგან ერთი გვერდის სწორი policy სხვა გვერდის rendering-ს ვერ ამტკიცებს.</p>
<p>დასკვნის ენა სამ დონედ დაყავით: დადასტურებული, სავარაუდო და მიუწვდომელი. დადასტურებულ ნაწილში შედის ნანახი header, შესაბამისი nonce ატრიბუტი და კონკრეტული script. სავარაუდო ნაწილში შედის framework-ის მოსალოდნელი ქცევა, რომელიც source ან authenticated test-ით არ შემოწმებულა. მიუწვდომელ ნაწილში შედის private route, server log, repository history და სხვა გარემო. ეს დაყოფა ბიზნესის მფლობელს აძლევს სწორ შემდეგ ნაბიჯს და არ ქმნის სრული უსაფრთხოების ილუზიას.</p>

<h2 id="limitations">რა შეზღუდვები აქვს CSP და nonce მნიშვნელობის review-ს?</h2>
<p>CSP შეიძლება სწორად იყოს მიწოდებული და მაინც დარჩეს authorization, მონაცემთა იზოლაციის, dependency-ის ან server-side ლოგიკის პრობლემა. საჯარო URL აჩვენებს მხოლოდ იმას, რასაც ჩვეულებრივი visitor იღებს. ის ვერ ადასტურებს ყველა API route-ს, private admin flow-ს, secret-ის დაცვას ან source repository-ის მდგომარეობას. საჯარო URL scan-ის საზღვრები ანგარიშში ცალკე უნდა ჩაიწეროს.</p>
<p>Nonce-ის არსებობა არც თავისთავად ნიშნავს, რომ ყველა inline კოდი სანდოა. თუ attacker-ს შეუძლია trusted template-ში თავისი შინაარსის შეტანა, ან თუ policy ზედმეტად ფართოა, ერთი header ვერ დახურავს ამ გზას. ასევე, კონკრეტული framework-ის rendering რეჟიმი, cache და edge layer შეიძლება გავლენას ახდენდეს იმაზე, როგორ იქმნება და გადადის მნიშვნელობა. საბოლოო დასკვნა უნდა აღწერდეს შემოწმებულ URL-ს, დროს, მეთოდს და იმას, რაც არ შემოწმებულა.</p>

<h2 id="faq">ხშირად დასმული კითხვები</h2>
<h3 id="faq-1">Nonce მუდმივი მნიშვნელობა უნდა იყოს?</h3>
<p>არა. nonce კონკრეტულ response-სა და მის დაშვებულ script-ს უნდა უკავშირდებოდეს. მუდმივი მნიშვნელობა ან ყველა გვერდზე გამეორება მიმოხილვისთვის სერიოზული კითხვაა და არა უსაფრთხო default.</p>
<h3 id="faq-2">CSP ავტომატურად იცავს მთელ აპს?</h3>
<p>არა. CSP ბრაუზერის რესურსების შესრულების პოლიტიკას ამკაცრებს, მაგრამ ვერ ამოწმებს backend authorization-ს, მონაცემთა ბაზის წესებს ან ყველა dependency-ს. ის უფრო ფართო მიმოხილვის ერთი კონტროლია.</p>
<h3 id="faq-3">Report-only საკმარისია release-მდე?</h3>
<p>Report-only დაკვირვებას ამარტივებს, თუმცა დარღვევას არ ბლოკავს. Release გადაწყვეტილებამდე გუნდმა უნდა იცოდეს, რომელი შეტყობინება გამოსწორდა, რომელი დარჩა გამონაკლისად და რატომ.</p>
