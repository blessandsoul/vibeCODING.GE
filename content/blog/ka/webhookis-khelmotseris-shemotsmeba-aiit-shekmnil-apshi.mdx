<h2 id="delivery-is-not-proof">რატომ არ არის webhook მიღება მტკიცებულება?</h2>
<p>Webhook არის HTTP მოთხოვნა, რომელსაც provider აგზავნის თქვენს endpoint-ზე. ქსელიდან მოსული ნებისმიერი მოთხოვნა შეიძლება იყოს შეცვლილი, განმეორებული ან სხვა წყაროდან გამოგზავნილი. აპლიკაციამ ჯერ უნდა დაადგინოს, რომ payload ხელმოწერა შეესაბამება provider საიდუმლო წესს, შემდეგ კი გადაწყვიტოს, რა შეიძლება გააკეთოს ამ მონაცემით.</p>
<p>AI-ით შექმნილ აპლიკაციაში გავრცელებული შეცდომაა JSON parse, ველების გადალაგება ან middleware გავლა ხელმოწერის შემოწმებამდე. ეს მოქმედებები შეიძლება შეცვალოს ის ბაიტები, რომლებზეც ხელმოწერა დაითვალა. <a href="https://docs.stripe.com/webhooks/signature">Stripe ოფიციალური დოკუმენტაცია</a> პირდაპირ უსვამს ხაზს raw request body საჭიროებას. ამიტომ review პირველ კითხვად ჩაწერეთ: რომელ ეტაპზე ინახება და რომელ ეტაპზე მოწმდება თავდაპირველი body?</p>

<h2 id="replay-and-idempotency">Replay და idempotency ცალკე საზღვარი</h2>
<p>ხელმოწერა პასუხობს კითხვას, შეიცვალა თუ არა payload და იცოდა თუ არა გამომგზავნმა secret წესი. ის თავისით არ ამბობს, უკვე დამუშავდა თუ არა ეს event. ხელმოწერილი payload ხელახლა გაგზავნამ შეიძლება ერთსა და იმავე ბიზნეს-მოქმედებას კვლავ მიაღწიოს, თუ handler-ს event ID, timestamp, deduplication ან შესაბამისი transaction boundary არ აქვს.</p>
<p><a href="https://docs.stripe.com/webhooks#best-practices">Stripe webhook საუკეთესო პრაქტიკის დოკუმენტაცია</a> duplicate delivery უსაფრთხო დამუშავებას ცალკე საკითხავად ასახელებს. ვალიდური retry განმეორებითი მოქმედების შეჩერების სახელმძღვანელო სწორედ ამ განსხვავებას აგრძელებს. სხვა სიტყვებით, verification არის შესასვლელი, ხოლო idempotency არის ის წესი, რომელიც უკვე შემოსულ event-ს ბიზნესის მდგომარეობის ორჯერ შეცვლას არ აძლევს.</p>
<p>თბილისის გამოგონილ ონლაინ-სერვისს შეიძლება subscription დასრულების webhook ორჯერ მიუვიდეს: ერთხელ provider retry-ით და ერთხელ ქსელის აღდგენის შემდეგ. თუ handler მხოლოდ ხელმოწერას ამოწმებს და event ID-ს არ იმახსოვრებს, იგი შეიძლება ორჯერ გაგზავნოს ელფოსტა ან არასწორად განაახლოს სტატუსი. ეს სასწავლო სცენარია და aiNOW კლიენტის შედეგს არ აღწერს.</p>

<h2 id="access-and-payment-boundary">Payment და access გადაწყვეტილების საზღვარი</h2>
<p>Webhook event შეიძლება შეიცავდეს payment ან subscription მდგომარეობას, მაგრამ აპლიკაციის წვდომის შეცვლა მაინც უნდა დაეყრდნოს provider დოკუმენტირებულ event type-ს, საკუთარ მონაცემთა მოდელს და მომხმარებლის იდენტობის შესაბამისობას. უბრალოდ ველის არსებობა ან წარმატებული HTTP პასუხი არ არის საკმარისი.</p>
<p>Payment webhook შემდეგ წვდომის მიცემის შემოწმება ცალკე უნდა წაიკითხოთ: იქ მთავარი კითხვა არის როდის შეიძლება subscription მდგომარეობა მომხმარებელზე აისახოს. დუბლირებული subscription event-ების თავიდან აცილება კი დაგეხმარებათ, delivery, event და business record ერთმანეთისგან არ აურიოთ.</p>

<h2 id="safe-test">როგორ გავაკეთოთ ტესტი ცოცხალი მომხმარებლის დაზიანების გარეშე?</h2>
<p>სატესტო შემოწმებაში გამოიყენეთ provider test mode, იზოლირებული endpoint ან წინასწარ დამტკიცებული fixture. არ გამოიყენოთ ნამდვილი customer მონაცემი, არ შეცვალოთ რეალური გადახდის მდგომარეობა და არ გადააგზავნოთ უცნობი payload production-ზე. endpoint timeout და პასუხის კოდი მხოლოდ ერთ ნაწილს ამოწმებს, ამიტომ შედეგი ცალკე ჩაიწერეთ verification log-ში.</p>
<p>პრაქტიკული pass/fail ტესტი შეიძლება ასეთი იყოს: იგივე fixture გაიგზავნოს ერთხელ უცვლელად და ერთხელ ერთი ბაიტის ცვლილებით. პირველმა უნდა მიაღწიოს მხოლოდ მოსალოდნელ processing-ს, მეორემ კი უარი უნდა მიიღოს ისე, რომ business record არ შეიცვალოს. შემდეგ იგივე ვალიდური fixture განმეორებით გაუშვით შეთანხმებულ test გარემოში და ნახეთ, ქმნის თუ არა წესრიგი ერთზე მეტ მოქმედებას. შედეგი მხოლოდ იმ გარემოს ეკუთვნის, რომელიც აღწერეთ.</p>
<p>Public endpoint rate limiting დამატებითი კონტროლია, მაგრამ იგი ვერ ჩაანაცვლებს signature verification-ს. სიჩქარის შეზღუდვა ამცირებს დატვირთვას, authenticity კი სხვა კითხვაა.</p>

<h2 id="review-record">Webhook review ჩანაწერი</h2>
<p>საბოლოო ჩანაწერში პირველ ხაზზე მიუთითეთ provider, endpoint, გარემო და მიღებული documentation ბმული. შემდეგ აღწერეთ raw body გზა: სად შედის request, რომელი middleware ეხება payload-ს, სად ხდება verification და რომელ ეტაპზე გადადის event queue-ში. ასეთი სქემა ტექნიკურ გუნდს აჩვენებს, სად შეიძლება შეიცვალოს bytes და სად შეიძლება მოხდეს business action.</p>
<p>Signature ტესტს დაურთეთ ვალიდური fixture, შეცვლილი fixture და დაკარგული header შედეგი. თითოეულ ვარიანტში ჩაიწეროს HTTP პასუხი, log უსაფრთხო ჩანაწერი და მონაცემთა მდგომარეობა. ვალიდური fixture ორჯერ გაგზავნა ცალკე ტესტია: verification შეიძლება ორჯერ გაიაროს, მაგრამ idempotency წესმა განმეორებითი შედეგი უნდა გააჩეროს. ნამდვილი მომხმარებლის მონაცემი ან მოქმედი payment credential ასეთ ტესტში არ გამოიყენოთ.</p>
<p>Provider შეცვლისას ნუ გადაიტანთ ძველ header სახელს, timestamp წესს ან SDK wrapper-ს ავტომატურად. ახალი დოკუმენტაცია, secret გარემო, raw body ფორმატი და უარის გზა ცალკე შეადარეთ. ერთი საერთო აბსტრაქცია რამდენიმე provider-ს შეიძლება აერთიანებდეს, თუმცა provider-specific verification უნდა დარჩეს მკაფიო და წასაკითხი.</p>
<p>Release handover-ში გამოყავით სამი მფლობელი: endpoint კოდის პასუხისმგებელი, secret მმართველი და business action დამმტკიცებელი. მცირე გუნდში ერთი ადამიანი შეიძლება რამდენიმე როლს ასრულებდეს, მაგრამ ჩანაწერში როლები მაინც ცალკე უნდა ჩანდეს. ცვლილების შემდეგ შეინახეთ commit ან deployment identifier, test გარემო და დარჩენილი unknown-ები. ეს მიდგომა ხელს უშლის ხელმოწერის არსებობასთან ერთად მთელი integration დაუმსახურებელად დამოწმებას.</p>
<p>სარევიზიო ცხრილში ჩაწერეთ provider, endpoint, გარემო, event type, signature header, secret საცავი და raw body დამუშავების ადგილი. ცხრილში არ ჩაწეროთ მოქმედი secret ან მომხმარებლის payload. უსაფრთხო ჩანაწერი აღწერს ველის სახელს, მფლობელს, ტესტის მეთოდს და შედეგს. ასეთი ფორმა საკმარისია შემდეგი review-ისთვის და ამცირებს მგრძნობიარე მონაცემის ხელახლა გავრცელების რისკს.</p>
<p>უარის სცენარების ჯგუფი მოიცავს შეცვლილ body-ს, ძველ timestamp-ს, უცნობ signature-ს, დაკარგულ header-ს, არასწორ endpoint secret-ს და სხვა provider ფორმატს. თითოეულ სცენარს უნდა ჰქონდეს უარის პასუხი, უსაფრთხო log და ნულოვანი business mutation. ცალკე შეამოწმეთ timeout, queue retry და worker restart, რადგან edge-ზე სწორი უარი საბოლოო დამუშავების წესს ვერ ამტკიცებს.</p>
<p>დადასტურებული event შემდეგ მონაცემთა ცვლილება აღწერეთ transaction ენით: რომელი record იკითხება, რომელი მდგომარეობა იცვლება, რომელი event ID ინახება და რა ხდება წარუმატებელი write დროს. პირდაპირი მოქმედება, queue და batch worker განსხვავებულ რისკს ქმნის. idempotency key შენახვის ადგილი, ვადის წესი და ხელახლა გაშვების შედეგი ცალკე დოკუმენტად დატოვეთ.</p>
<p>Provider documentation-ში მოძებნეთ ხელმოწერის ფორმატი, raw body მოთხოვნა, timestamp წესები, retry პირობები და test mode შეზღუდვები. წყაროს ბმული დაურთეთ ყველა ასეთ გადაწყვეტილებას. ინტეგრაციის კოდი შეიძლება იცვლებოდეს, ხოლო ძველი ჩანაწერი უცვლელი დარჩეს; ამიტომ receipt-ში მიუთითეთ შემოწმების თარიღი და გამოყენებული commit.</p>
<p>მფლობელის მიერ ხელმოწერილ მიღების ფურცელში ცალ-ცალკე ჩაიწეროს, მიღებულია თუ არა შეტყობინება, გადამოწმდა თუ არა ხელმოწერა, მიღებულია თუ არა მოვლენა და შესრულდა თუ არა ბიზნესქმედება. თითოეული მდგომარეობა დამოუკიდებელ მტკიცებულებას მოითხოვს. წარმატებული HTTP პასუხი მხოლოდ მიღებას ადასტურებს; ის არ ადასტურებს გადახდას, წვდომის მინიჭებას ან შემოსავალს. ასეთი საზღვარი იცავს გუნდს ზედმეტი დასკვნისგან და ამარტივებს პრობლემის აღმოჩენას.</p>

<h2 id="limitations">რა შეზღუდვები აქვს webhook საჯარო review-ს?</h2>
<p>საჯარო URL-ით შეიძლება endpoint არსებობა, პასუხის ზოგადი ქცევა ან გამოქვეყნებული documentation შეამოწმოთ, მაგრამ secret რეალური დაცვა, raw body middleware, queue worker და მონაცემთა ბაზის transaction ჩვეულებრივ ავტორიზებულ წვდომას მოითხოვს. ამიტომ ანგარიშში მკაფიოდ ჩაწერეთ, რა იყო დაკვირვებული და რა არ იყო ხელმისაწვდომი.</p>
<p>Provider SDK გამოყენებაც არ არის ავტომატური გარანტია: არასწორი secret, არასწორი გარემო, body parser რიგი ან custom wrapper კვლავ შეიძლება შეცდომას ქმნიდეს. ასევე, სწრაფი უარი კარგია, მაგრამ queue-ში გადატანილი event მოგვიანებით დამუშავებას საკუთარი retry და deduplication წესები სჭირდება. Production handover ჩეკლისტი დაგეხმარებათ ამ პასუხისმგებლობების მფლობელი და აღდგენის გზა წერილობით დარჩეს.</p>

<h2 id="faq">ხშირად დასმული კითხვები</h2>
<h3 id="faq-1">თუ webhook-ს ვიღებთ, უკვე provider-იდან არის?</h3>
<p>არა. მიღებული HTTP მოთხოვნა მხოლოდ delivery-ს აჩვენებს. აპლიკაციამ provider წესით უნდა გადაამოწმოს signature, secret, raw body და საჭირო freshness ან replay კონტროლი.</p>
<h3 id="faq-2">Signature verification აგვარებს duplicate event-ს?</h3>
<p>არა. ხელმოწერა payload სანდოობის შემოწმებაა, ხოლო duplicate event მართვა idempotency-სა და event მდგომარეობას ეკუთვნის. ორივე კონტროლი ცალკე უნდა ჩანდეს.</p>
<h3 id="faq-3">შეიძლება verification ტესტი production-ზე გავუშვათ?</h3>
<p>მხოლოდ მაშინ, როცა provider-ისა და აპლიკაციის მფლობელმა ზუსტად განსაზღვრა არადესტრუქციული ტესტი. ჩვეულებრივ უსაფრთხო დასაწყისი არის test mode, fixture ან იზოლირებული endpoint, არა ნამდვილი მომხმარებლის მდგომარეობის შეცვლა.</p>
