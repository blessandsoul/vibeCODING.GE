<p><strong>პირდაპირი პასუხი:</strong> CSRF review ამოწმებს, შეუძლია თუ არა სხვა origin გვერდს უკვე ავტორიზებული ბრაუზერის გამოყენებით ანგარიშის შეცვლის მოთხოვნის გამოწვევა. მხოლოდ CSRF ტოკენის არსებობა საკმარისი დასკვნა არ არის. უნდა შემოწმდეს კონკრეტული state-changing route, cookie ქცევა, token შემოწმება და ისიც, ხომ არ აგენერირებს კლიენტის კოდი მოთხოვნას თავდამსხმელის მიერ კონტროლირებადი input-იდან. <a href="/contact">vibeCODING scoped review მოითხოვეთ</a>, თუ გჭირდებათ არსებული AI-ით შექმნილი აპის ამ საზღვრით შემოწმება.</p>

<h2 id="csrf-meaning">რას ამოწმებს CSRF review?</h2>
<p>Cross-Site Request Forgery, ანუ CSRF, არის სცენარი, როცა მომხმარებელი ერთ საიტზე შესულია, ხოლო სხვა საიტი მის ბრაუზერს სანდო აპის სახელით მოქმედების შესრულებას ატყუებს. საფრთხე ეხება მოქმედებას, რომელიც მონაცემს ცვლის: ელფოსტის მისამართის შეცვლას, პაროლის განახლებას, მიწერის გაგზავნას, გამოწერის შეწყვეტას ან ადმინისტრაციული პარამეტრის შეცვლას. საკითხი განსხვავდება XSS-ისგან. XSS კოდის შესრულებას ეხება, CSRF კი უკვე არსებული სესიის გამოყენებით არასასურველ მოთხოვნას.</p>
<p><a href="https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html">OWASP CSRF Prevention Cheat Sheet</a> ხაზს უსვამს, რომ დაცვა უნდა მიებას იმ მოთხოვნებს, რომლებიც მდგომარეობას ცვლის. უსაფრთხოების review-ში ამიტომ თავიდანვე უნდა შეიქმნას route-ების სია და თითოეულ მოქმედებას მიეთითოს, რა მონაცემს ცვლის, როგორ იდენტიფიცირდება მომხმარებელი და რა მტკიცებულება ადასტურებს დაცვას.</p>

<h2 id="review-sequence">უსაფრთხო შემოწმების თანმიმდევრობა</h2>
<p>პრაქტიკული review უნდა იყოს განმეორებადი და შეზღუდული. <a href="https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/06-Session_Management_Testing/06-Testing_for_CSRF">OWASP Web Security Testing Guide</a> CSRF ტესტირებას სესიის მართვის კონტექსტში განიხილავს. ამ წყაროს გამოყენებით შემოწმება ასე დაალაგეთ:</p>
<ol>
  <li><strong>დაასახელეთ მოქმედება:</strong> აირჩიეთ ერთი მოთხოვნა, რომელიც მონაცემს ცვლის, ჩაიწერეთ method, route, მომხმარებლის როლი და მოსალოდნელი შედეგი.</li>
  <li><strong>გააცალკევეთ მტკიცებულება:</strong> შეინახეთ request მაგალითი token-ით, მის გარეშე და არასწორი მნიშვნელობით. მგრძნობიარე cookie ან token სრულად ანგარიშში არ გადაიტანოთ.</li>
  <li><strong>შეადარეთ პასუხები:</strong> დაცულ შემთხვევაში server-მა მოთხოვნა უნდა უარყოს ან არ შეასრულოს ცვლილება. მხოლოდ განსხვავებული status code არ არის საკმარისი, თუ მონაცემი მაინც შეიცვალა.</li>
  <li><strong>გაიმეორეთ სხვა გზით:</strong> იგივე ბიზნეს-მოქმედება შეამოწმეთ ბრაუზერის ფორმით, fetch-ით და საჭიროების შემთხვევაში სხვა როლით. მიზანია დამცავი კონტროლის რეალური საზღვრის დანახვა.</li>
  <li><strong>დააფიქსირეთ უცნობი:</strong> თუ private route, native app, proxy ან მესამე მხარის კლიენტი არ შემოწმებულა, ის ღია საკითხად დატოვეთ.</li>
</ol>
<p>ტესტი უნდა შესრულდეს მხოლოდ აპის მფლობელის მიერ შეთანხმებულ გარემოში. ცოცხალ მომხმარებელზე ცვლილების გამოწვევა, უცნობი origin გამოყენება ან რეალური გადახდის flow შეხება ცალკე ავტორიზაციას მოითხოვს.</p>

<h2 id="token-cookie-comparison">ტოკენი, SameSite და custom header</h2>
<p>CSRF ტოკენი server-ს აძლევს შესაძლებლობას, მოთხოვნა შეადაროს სესიასთან ან გვერდზე გაცემულ საიდუმლო მნიშვნელობას. SameSite cookie წესი ბრაუზერს ეუბნება, რა კონტექსტში გააგზავნოს cookie. custom header მოთხოვნა კი ხშირად ართულებს უბრალო cross-site ფორმის გამოყენებას. ეს კონტროლები ერთი და იგივე არ არის და არც ყველა კლიენტზე ერთნაირად მუშაობს.</p>
<p><a href="https://owasp.org/projects/asvs?tab=main">OWASP Application Security Verification Standard</a> კონტროლების შემოწმებას კონტექსტში გვთავაზობს. ამიტომ ანგარიშში ჩაწერეთ, რომელი layer ნახეთ და რომელი არა. მაგალითად, cookie-ს SameSite ატრიბუტი შეიძლება სწორად ჩანდეს, მაგრამ server მაინც არ ამოწმებდეს მომხმარებლის უფლებას კონკრეტულ ობიექტზე. პირიქითაც შესაძლებელია: token სწორად მოწმდებოდეს, მაგრამ client-side flow-მა untrusted URL-იდან მოქმედების მიზანი შეცვალოს.</p>
<p>განსაკუთრებული ყურადღება მიაქციეთ client-side CSRF-ს. OWASP მითითებით, attacker-controlled URL ან სხვა input შეიძლება JavaScript-ს სანდო API-ზე მოთხოვნის აგენერირებინოს. ასეთ შემთხვევაში token ან custom header შესაძლოა თვითონ აპმა დაამატოს, ამიტომ მხოლოდ მათი არსებობა საკმარისი მტკიცებულება აღარ არის.</p>

<h3 id="decision-rule">რომელი შედეგი ითხოვს გამოსწორებას release-მდე?</h3>
<p>Release გადაწყვეტილება სჯობს დაიყოს მტკიცებულების დონეებად. <strong>დადასტურებული პრობლემა</strong> არის შემთხვევა, როცა ავტორიზებული სესიის პირობებში შეთანხმებული ტესტი state-changing მოქმედებას token გარეშე ან არასწორი კონტექსტიდან ასრულებს. <strong>სავარაუდო რისკი</strong> არის route, რომლის დამცავი კონტროლი კოდში ჩანს, მაგრამ იმავე კონტროლის მოქმედება ვერ დადასტურდა ნებადართული გარემოს გარეშე. <strong>უცნობი</strong> რჩება ყველაფერი, რაც private API-ს, სხვა client-ს ან არანახულ deployment-ს ეხება.</p>
<p>პრიორიტეტი მიანიჭეთ მოქმედებას და არა მხოლოდ ტექნიკურ სახელს. პაროლის, წვდომის, ფულის ან ორგანიზაციის წევრობის ცვლილება უფრო მკაცრ გადაწყვეტილებას ითხოვს, ვიდრე არაკრიტიკული UI პარამეტრი. ანგარიშში მიუთითეთ user role, route, ზემოქმედების შესაძლო ტიპი, მტკიცებულება, გამოსწორების მფლობელი და ხელახალი შემოწმების პირობა. სიტყვა „დაცულია“ გამოიყენეთ მხოლოდ კონკრეტულ შემოწმებულ scope-ზე.</p>

<h2 id="common-mistakes">რა შეცდომები აბნევს AI-ით შექმნილი აპის CSRF review-ს?</h2>
<ul>
  <li>მხოლოდ frontend ფორმის დათვალიერება და backend route გამოტოვება.</li>
  <li>GET მოთხოვნის გამოყენება მონაცემის შესაცვლელად და შემდეგ token დამატებით პრობლემის დაფარვა.</li>
  <li>CSRF დაცვის XSS დაცვის შემცვლელად მიჩნევა.</li>
  <li>SameSite ჩართვა ისე, რომ სხვა client-ები და cross-origin ბიზნეს-მოთხოვნები არ შემოწმდეს.</li>
  <li>token სრულად ჩაწერა ანგარიშში, სადაც ის შემდეგ ახალი საიდუმლო ხდება.</li>
  <li>ერთ route-ზე წარმატებული ტესტის მთელ აპზე განზოგადება.</li>
</ul>
<p>AI builder მიერ გენერირებული კოდი შეიძლება ერთსა და იმავე მოქმედებას რამდენიმე helper-ით ასრულებდეს. ამიტომ review სამუშაო ფურცელი route-ს, ბიზნეს-მოქმედებას და მტკიცებულებას ერთმანეთს უნდა უკავშირებდეს, ვიდრე მხოლოდ ფაილის სახელს ან framework default-ს დაეყრდნობოდეს.</p>

<h2 id="product-boundary">რას მოიცავს vibeCODING scoped review?</h2>
