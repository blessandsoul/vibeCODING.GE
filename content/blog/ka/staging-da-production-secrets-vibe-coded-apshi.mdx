<p><strong>პირდაპირი პასუხი:</strong> staging და production გარემო მხოლოდ ორი განსხვავებული URL არ არის. ისინი უნდა განსხვავდებოდეს მონაცემებით, secrets-ით, წვდომით, deployment წესით და rollback გზით. ცვლადის სახელში „secret“ არ ნიშნავს, რომ ის browser bundle-ში ან preview build-ში არ ჩანს. release-მდე შეადარეთ გარემოების კონფიგურაცია, შეამოწმეთ საჯარო output და ჩაწერეთ, ვის შეუძლია ცვლილება. არსებული აპის ამ საზღვრის შესაფასებლად <a href="/contact">vibeCODING scoped review მოთხოვნა გააგზავნეთ</a>.</p>

<h2 id="why-separation-matters">რატომ არის გარემოების გამიჯვნა მნიშვნელოვანი?</h2>
<p>Staging არის სივრცე, სადაც გუნდი ცვლის აპს კონტროლირებად მონაცემებსა და სატესტო ინტეგრაციებთან ერთად. Production არის გარემო, რომელსაც ნამდვილი მომხმარებელი, business record ან გარე provider შეიძლება იყენებდეს. თუ ორივე ერთ secret-ს, database-ს ან admin account-ს იყენებს, სატესტო ცვლილება შეიძლება რეალურ მდგომარეობას შეეხოს.</p>
<p>AI builder-მა შეიძლება კონფიგურაცია გარეგნულად სწორად შექმნას, მაგრამ ვერ გაითვალისწინოს თქვენი billing-ის, მონაცემთა შენახვის ან release-ის პასუხისმგებლობის წესი. ამიტომ dashboard-ის ერთიანი „environment variables“ გვერდი თავისთავად გამიჯვნის მტკიცებულება არ არის. Staging-ის ცალკე მომზადების სახელმძღვანელო სწორედ ამ განსხვავების აღწერით იწყება.</p>

<h2 id="public-vs-secret">რა განსხვავებაა public და secret ცვლადს შორის?</h2>
<p>Public configuration შეიძლება კლიენტმა იცოდეს, მაგალითად public API endpoint ან browser-სთვის განკუთვნილი identifier. Secret კი ისეთი მნიშვნელობაა, რომლის გამჟღავნებაც საშუალებას აძლევს არაავტორიზებულ მხარეს მოქმედება შეასრულოს ან მონაცემზე წვდომა მიიღოს. სახელში `PUBLIC`, `NEXT_PUBLIC` ან მსგავსი პრეფიქსი უსაფრთხოების კლასს არ ქმნის; საბოლოო პასუხს build მიერ კლიენტისთვის მიწოდებული output იძლევა.</p>

<p><a href="https://vercel.com/docs/environment-variables">Vercel-ის ოფიციალურ დოკუმენტაციაში</a> environment-specific ცვლადების გამოყენება ცალკეა აღწერილი, თუმცა provider-ის ფუნქციის არსებობა არ ამტკიცებს, რომ თქვენი კოდი მას სწორ scope-ში იყენებს. variable-ის სახელი, dashboard-ის მნიშვნელობა და build-ის შედეგი სამ სხვადასხვა შემოწმებად ჩაწერეთ.</p>

<h2 id="four-gates">ოთხი პრაქტიკული gate release-მდე</h2>
<p>Release checklist-ის მიზანია, გარემოებს შორის განსხვავებები იყოს განზრახული, ხილული და პასუხისმგებელ ადამიანთან მიბმული.</p>
<ol>
  <li><strong>ინვენტარი:</strong> ჩამოწერეთ ყველა environment, branch, deployment job, provider და database, რომელსაც build შეიძლება შეეხოს.</li>
  <li><strong>კლასიფიკაცია:</strong> თითოეულ ცვლადს მიუთითეთ public, server secret, test-only ან unknown სტატუსი. უცნობი მნიშვნელობა release-ready არ არის.</li>
  <li><strong>მიღების ტესტი:</strong> გადაამოწმეთ browser bundle, logs, source map და preview URL, რომ server secret კლიენტამდე არ მიდის.</li>
  <li><strong>მფლობელი და დაბრუნება:</strong> ჩაწერეთ, ვინ ამტკიცებს production ცვლილებას, როგორ უქმდება წვდომა და როგორ ბრუნდება წინა ვერსიაზე.</li>
</ol>
<p>ტესტის თითოეულ შედეგს გარემოს სახელი და დრო დაურთეთ. ერთი წარმატებული preview არ ნიშნავს, რომ production secret-ები ან მონაცემთა schema სწორად არის გამიჯნული. Production handover ჩეკლისტი ეხმარება არატექნიკურ მფლობელს, ეს ინფორმაცია მხოლოდ ზეპირ შეთანხმებად არ დარჩეს.</p>

<h2 id="preview-risk">Preview build ცალკე რისკი</h2>
<p>Preview deployment ხშირად იღებს branch კოდს და ავტომატურად იყენებს რომელიმე environment ცვლადებს. თუ წესები ბუნდოვანია, ახალი feature შეიძლება production API-ს დაეკავშიროს, ხოლო log-ში ან bundle-ში test და live მონაცემები აირიოს. preview URL არსებობა უსაფრთხო გარემოს მტკიცებულება არ არის.</p>
<p><a href="https://docs.github.com/en/actions/deployment/targeting-different-environments/using-environments-for-deployment">GitHub ოფიციალური დოკუმენტაცია</a> deployment environment-ს, protection rule-სა და environment secret-ს ცალკე ცნებებად აღწერს. ეს ნიშნავს, რომ CI/CD-ში დაცული secret არსებობა მაინც მოითხოვს იმის შემოწმებას, რომელ job-ს აქვს მისი წაკითხვის უფლება. branch protection, reviewer და deployment target ერთ ჩანაწერში დააკავშირეთ, რათა შემთხვევითი merge release პირდაპირ გზად არ იქცეს.</p>
<p>თბილისის გამოგონილ გუნდს შეიძლება ჰქონდეს preview, რომელიც test database-ს იყენებს, მაგრამ payment provider live key დარჩა. გვერდი მუშაობს, ამიტომ პრობლემა მხოლოდ მაშინ ჩანს, როცა სატესტო ქმედება რეალურ billing flow-ს შეეხება. ეს სასწავლო სცენარია და aiNOW კლიენტის შემთხვევას არ აღწერს.</p>

<h2 id="exposure-response">რა ვქნათ, თუ secret უკვე გამოჩნდა?</h2>
<p>გამოჩენილი secret წაშლა git history-დან ან dashboard-იდან საკმარისი არ არის. ჯერ ჩათვალეთ იგი კომპრომეტირებულად, განსაზღვრეთ რა რესურსზე ჰქონდა წვდომა, გააუქმეთ ან შეცვალეთ provider წესით და შემდეგ მოძებნეთ ძველი build, log, cache და preview ასლები. Exposed secret rotation სახელმძღვანელო ამ პროცესს ცალკე ხსნის.</p>
<p>თუ ძველი preview URL ჯერ კიდევ საჯაროა, ახალი secret გაკეთება მარტო ვერ ხურავს მას. Deployment უნდა გაუქმდეს, cache და log შენახვის წესი გადაიხედოს, ხოლო მოქმედი key scope შემცირდეს. ძველი preview deployment გაწმენდა დაგეხმარებათ, rotation და exposure cleanup ერთმანეთში არ აურიოთ.</p>

<h2 id="dependencies-and-handover">როგორ უკავშირდება ეს dependency-სა და handover-ს?</h2>
<p>Environment separation ვერ აგვარებს მესამე მხარის პაკეტის ან build plugin რისკს. თუ dependency-ს შეუძლია build-time-ში secret ჩასმა, output შემოწმება ისევ საჭიროა. <a href="https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html">OWASP Secrets Management Cheat Sheet</a> lifecycle-სა და წვდომის კონტროლს ცალკე განიხილავს, ხოლო AI-ით შექმნილი კოდის dependency შემოწმება ამ რისკს environment ცალკე ნაწილად უკავშირებს.</p>
<p>Handover-ში უნდა ჩანდეს environment სახელი, variable კლასიფიკაცია, deployment დამტკიცების გზა, rotation პასუხისმგებელი და rollback მოქმედება. საიდუმლო მნიშვნელობა თვითონ დოკუმენტში არ ჩაწეროთ. მიუთითეთ მხოლოდ საცავის ან secret manager ადგილი, რომელსაც უფლებამოსილი ადამიანი ხედავს. Review შედეგი აღწერს შემოწმებულ boundary-ს და არა მთელი სისტემის მუდმივ გარანტიას.</p>

<h2 id="release-record">Environment release სამუშაო ფურცელი</h2>
<p>პირველ ეტაპზე ჩამოწერეთ გარემოს სახელი, branch, deployment provider, database, storage და გარე ინტეგრაციები. თითოეულ ჩანაწერს მიამაგრეთ გამოყენების მიზანი: browser configuration, server runtime, test credential, production secret ან უცნობი მნიშვნელობა. უცნობი სტატუსი არ არის უარყოფითი შეფასება; ეს არის დამატებითი შემოწმების მოთხოვნა, რომელიც release-მდე უნდა დაიხუროს.</p>
<p>მეორე ეტაპზე შეადარეთ staging და production-ის განსხვავებები და მათი მიზეზები. Test database-ის მისამართი, payment provider-ის რეჟიმი, email recipient, storage bucket, webhook endpoint და admin role ცალკე ველებად ჩაწერეთ. საერთო მნიშვნელობა მხოლოდ მაშინ დატოვეთ, როცა მფლობელი აღწერს საჭიროებას, scope-სა და rollback-ს. საერთო credential-ის გამოყენება მარტივია, მაგრამ გარემოების შეცდომით არევის შემთხვევაში ზიანის მასშტაბს ზრდის.</p>
<p>მესამე ეტაპზე შეამოწმეთ საბოლოო output და არა მხოლოდ configuration screen. გახსენით preview HTML, JavaScript bundle, source map, network request და build log. მოძებნეთ server secret, service credential ან შიდა signing key კვალი. აღმოჩენის შემთხვევაში შეჩერდეს release, განისაზღვროს credential წვდომა, დაიწყოს rotation და მხოლოდ შემდეგ განახლდეს preview. კლიენტის bundle-ში ხილული key შემოწმება ამ სამუშაოს დამატებითი კონტექსტია.</p>
<p>მეოთხე ეტაპზე ჩაწერეთ release approval და დაბრუნების გზა. ვინ ამტკიცებს merge-ს? ვინ ხედავს production secret-ს? ვინ აუქმებს preview deployment-ს? ვინ ადასტურებს rollback წარმატებას? პასუხი შეიძლება ერთ ადამიანს ეკუთვნოდეს, თუმცა დამტკიცების, წვდომის და აღდგენის მოქმედებები მაინც ცალკე უნდა იყოს აღწერილი. ასეთი ჩანაწერი არ ითხოვს secret ტექსტის გამჟღავნებას და ხელს უშლის პირად მეხსიერებაზე დამოკიდებულებას.</p>
<p>მეხუთე ეტაპზე დააფიქსირეთ დროებითი გამონაკლისი და ვადა. მაგალითად, migration-ისთვის დამატებული permission, test provider დროებითი endpoint ან preview განსაკუთრებული variable უნდა ჰქონდეს მფლობელი და გაუქმების პირობა. ვადის გარეშე გამონაკლისი ჩუმად მუდმივ კონფიგურაციად იქცევა. Test data-სა და admin account გაწმენდა ამავე release checklist ნაწილია, რადგან მხოლოდ variable გაყოფა არასაკმარისია.</p>
<p>გარემოების აღწერისას გამოიყენეთ ერთი სტანდარტული ფორმა: მიზანი, მონაცემთა კლასი, წვდომის როლი, ცვლილების გზა, შემოწმების შედეგი და დაბრუნების პირობა. მიზნის ველი პასუხობს კითხვას, რატომ არსებობს ცვლადი. მონაცემთა კლასი აჩვენებს public, test ან secret მდგომარეობას. წვდომის როლი აღწერს ჯგუფს და არა ერთ პირად credential-ს. ცვლილების გზა აკავშირებს pull request-ს, reviewer-სა და deployment-ს. შემოწმების შედეგი ინახავს ზუსტ გარემოს. დაბრუნების პირობა განსაზღვრავს rollback-ს.</p>
<p>Preview build მიმოხილვა გააკეთეთ რამდენიმე მიმართულებით: საწყისი HTML, JavaScript bundle, source map, network request, browser storage, cookie, log და error report. საჯარო პასუხში ნაპოვნი მნიშვნელობა ჩაითვალოს exposure signal-ად, სანამ server-side გამოყენება ცალკე არ დადასტურდება. სასწავლო ანგარიშში არ ჩასვათ სრული credential, token ან customer record. საკმარისია redacted მნიშვნელობა, მდებარეობა, დრო და შესაბამისი provider.</p>
<p>გამოქვეყნების გზაზე ჩაიწეროს branch-ის წესები, ცვლილების დამტკიცების ეტაპი, გარემოს დაცვა, აგების ბრძანება, არტეფაქტების საცავი და გამოშვების გამშვები პირობა. ავტომატური merge არ უნდა აძლევდეს preview-ს production data-ს გამოყენების შესაძლებლობას. production deploy-ს უნდა ჰქონდეს პასუხისმგებელი მფლობელი, ცვლილების იდენტიფიკატორი და დაბრუნების გეგმა. test გარემო ვერ ჩაითვალოს უსაფრთხო სივრცედ, თუ ნამდვილი payment, email ან webhook provider პირდაპირ live რეჟიმში მუშაობს.</p>
<p>Secret-ის შეცვლისას ცალ-ცალკე აღწერეთ აღმოჩენა, წვდომის შეფასება, გაუქმება, rotation, ძველი ასლების ძებნა და აღდგენის ტესტი. მხოლოდ dashboard value-ის წაშლა არასაკმარისია, რადგან ძველი build ან preview შესაძლოა ისევ არსებობდეს. repository history, CI log, cache, artifact და backup ცალკე სიად შეამოწმეთ. თითოეულ მოქმედებას დაურთეთ მფლობელი, დრო და შემდგომი დადასტურება.</p>
<p>Release ბოლოს მფლობელს მიაწოდეთ მოკლე acceptance sheet: რა შემოწმდა, რა გავიდა, რა ჩავარდა, რა დარჩა unknown და რომელი გადაწყვეტილება ელოდება ადამიანს. სტატუსი „მუშაობს“ არ ნიშნავს სტატუსს „production-ready“. ფუნქციური დემო შეიძლება success-ს აჩვენებდეს არასწორი გარემოთი, ზედმეტი წვდომით ან დაუცველი output-ით. საბოლოო შეფასება მხოლოდ შემოწმებული evidence ფარგლებში დაწერეთ.</p>

<h2 id="limitations">რა შეზღუდვები აქვს ამ checklist-ს?</h2>
<p>Checklist ვერ დაამტკიცებს, რომ ყველა secret ოდესმე არსებულ log-ში წაშლილია, რომ ყველა repository collaborator სწორად არის მართული ან რომ ყველა third-party provider permission მინიმალურია. ასევე, საჯარო bundle-ის სისუფთავე ვერ ადასტურებს server-side route-ის სწორ authorization-ს. საჭიროების შემთხვევაში ავტორიზებული source, CI/CD და provider review ცალკე scope-ად განსაზღვრეთ.</p>
<p>Provider UI, variable სახელები და release feature-ები შეიძლება შეიცვალოს. ამიტომ ანგარიშში დააფიქსირეთ შემოწმების თარიღი, environment, commit ან deployment identifier და ის გვერდები, რომლებიც არ იყო ხელმისაწვდომი. unknown არ გადააკეთოთ pass-ად მხოლოდ იმიტომ, რომ ვიზუალურად ყველაფერი მუშაობს.</p>

<h2 id="faq">ხშირად დასმული კითხვები</h2>
<h3 id="faq-1">თუ ცვლადს secret ეწოდება, browser-ში ვერ გამოჩნდება?</h3>
<p>არა. კოდი შეიძლება build-ისას secret-ს კლიენტის bundle-ში ჩასვამდეს. უნდა შემოწმდეს საბოლოო HTML, JavaScript bundle, source map და runtime ქსელური პასუხები, არა მხოლოდ dashboard label.</p>
<h3 id="faq-2">Preview და production შეიძლება ერთ secret-ს იყენებდეს?</h3>
<p>ზოგიერთ ტექნიკურ შემთხვევაში ეს განზრახ გადაწყვეტილება შეიძლება იყოს, მაგრამ release review-ში უნდა არსებობდეს მკაფიო მიზეზი, მინიმალური scope და დაბრუნების გზა. ჩვეულებრივ საერთო credential გამოყენება გარემოების გამიჯვნის რისკს ზრდის.</p>
<h3 id="faq-3">Secret შეცვლა საკმარისია მისი გაჟონვის შემდეგ?</h3>
<p>არა. rotation შემდეგ ძველი build, preview, log, cache და repository history ცალკე უნდა შემოწმდეს. გამოჩენილი credential კომპრომეტირებულად ჩათვალეთ, სანამ მისი წვდომის ეფექტი არ შეფასდება.</p>
