<p><strong>პირდაპირი პასუხი:</strong> AI-ით შექმნილი სტარტაპის ტექნიკური due diligence უნდა პასუხობდეს სამ კითხვას: ვის ეკუთვნის და ვინ მართავს ცოცხალ სისტემას, რომელი რისკი დადასტურდა მტკიცებულებით და შეძლებს თუ არა ახალი მფლობელი აპის შეცვლასა და აღდგენას. გამართული დემო მომხმარებლის გზას აჩვენებს, მაგრამ ვერ ამტკიცებს მონაცემზე წვდომის წესს, სარეზერვო ასლის აღდგენის უნარს ან ანგარიშების გადაცემას. თუ შეძენის, ინვესტიციის ან გადაბარების წინ კონკრეტული აპის შეფასება გჭირდებათ, <a href="/contact">vibeCODING-ის შემოსაზღვრული მიმოხილვა მოითხოვეთ</a>.</p>

<h2 id="buyer-decision">რა არის მყიდველის ტექნიკური გადაწყვეტილება?</h2>
<p>მყიდველი კოდს ცალკე არ ყიდულობს. გარიგებასთან ერთად შეიძლება გადავიდეს დომენი, მონაცემთა ბაზა, მომხმარებელთა ვალდებულებები, გადახდის ინტეგრაცია, ჰოსტინგის ანგარიში და ცვლილებების გამოქვეყნების პასუხისმგებლობა. ტექნიკური შეფასების შედეგი ამიტომ უნდა იყოს გადაწყვეტილების ჩანაწერი: რა მივიღოთ არსებული სახით, რა გამოსწორდეს გარიგებამდე, რა დარჩეს პირობად და რის გამოც გარიგება შეჩერდეს. მხოლოდ „დასკანირებულია“ ან „კოდი AI-ით დაიწერა“ ასეთ გადაწყვეტილებას არ ემსახურება.</p>
<p>შესყიდვის ამოცანა განსხვავდება ჩვეულებრივი production handover-ისგან. გადაბარება აღწერს, როგორ გააგრძელებს გუნდი უკვე მიღებული სისტემის მუშაობას. Due diligence უფრო ადრე დგას: ჯერ უნდა გაირკვეს, რეალურად რას იძენს მყიდველი, რომელი მტკიცებულება მოიპოვება და რომელი გაურკვევლობა ცვლის გარიგების პირობებს. <a href="https://csrc.nist.gov/projects/ssdf">NIST-ის SSDF ჩარჩო</a> პროგრამული უზრუნველყოფის შექმნის, დაცვისა და ხარვეზებზე რეაგირების სამუშაოებს ერთ ენაზე აერთიანებს; აქ ის შეკითხვების ჩარჩოა და არა კონკრეტული სტარტაპისთვის ავტომატური სერტიფიკატი.</p>

<h2 id="evidence-register">მტკიცებულების ოთხი კლასი ერთ რეესტრში</h2>
<p>საკუთრებისა და უსაფრთხოების განხილვაში აღმოჩენა ყოველთვის ერთნაირი სიმტკიცის არ არის. ყველა მნიშვნელოვანი დასკვნა მიაბით წყაროს, თარიღს, წვდომის ფარგლებს და განმეორებადი შემოწმების გზას. რეესტრში წინასწარ გამოყავით ნანახი ფაქტი, გამყიდველის მიერ მოწოდებული დოკუმენტი, ზეპირი განმარტება და ჯერ მიუწვდომელი საკითხი. ასე მყიდველი არ გადააქცევს პასუხის არქონას დადასტურებულ დარღვევად.</p>

<p>მაგალითად, ფრაზა „აღდგენა შესაძლებელია“ საკმარისი არ არის. რეესტრში მიუთითეთ, როდის აღდგა მონაცემი ბოლოს, ვინ შეასრულა ტესტი, რომელ გარემოში და რა დარჩა დაუმტკიცებელი. თუ ასეთი ჩანაწერი არ არსებობს, ზუსტი ფორმულირებაა „აღდგენის მტკიცებულება არ მოგვეწოდა“. ეს ჯერ კიდევ არ ამტკიცებს, რომ აღდგენა შეუძლებელია. ცალკე შეგიძლიათ ნახოთ <a href="/ka/blog/database-backups-for-a-production-vibe-coded-application">სარეზერვო ასლისა და აღდგენის შემოწმება</a>.</p>

<h2 id="ownership-map">აქტივების საკუთრების რუკა</h2>
<p>დაიწყეთ იმ სისტემებით, რომელთა დაკარგვაც ახალ მფლობელს აპის მართვის გარეშე დატოვებს. მოითხოვეთ ანგარიშის მფლობელობის და ადმინისტრაციული უფლებების დადასტურება, მაგრამ არა პაროლების გაგზავნა ჩატში. ერთი ადამიანის სახელი არ უდრის ორგანიზაციის კონტროლს: შესაძლოა კოდი კომპანიის რეპოზიტორიაში იყოს, ხოლო დომენი ან გადახდის ანგარიში პირად პროფილზე დარჩეს.</p>
<ol>
  <li><strong>დომენი და DNS:</strong> ჩაიწეროს რეგისტრატორი, სამართავი ანგარიში, განახლების მფლობელი და ცვლილების უფლებამოსილი პირი.</li>
  <li><strong>კოდი და გამოქვეყნება:</strong> დადასტურდეს რეპოზიტორიის მფლობელი, production branch, build გზა და ვინ შეუძლია ახალი ვერსიის გაშვება ან დაბრუნება.</li>
  <li><strong>მონაცემები:</strong> განისაზღვროს ბაზის, საცავისა და სარეზერვო ასლების ანგარიშები, წვდომის წესები და აღდგენის პასუხისმგებელი.</li>
  <li><strong>გარე ინტეგრაციები:</strong> ცალკე აღირიცხოს გადახდა, ელფოსტა, ანალიტიკა და API გასაღებები; გაირკვეს, შეიძლება თუ არა მათი გადაცემა ან ახალი გასაღებებით უსაფრთხო ჩანაცვლება.</li>
  <li><strong>გამომავალი ვალდებულებები:</strong> აღირიცხოს ვის ეკუთვნის ღია ხარვეზის გასწორება, მომხმარებლის ინფორმირება და წვდომის გაუქმება გარიგების შემდეგ.</li>
</ol>
<p>ეს რუკა გადაბარების სიაში გადაიტანეთ მხოლოდ მას შემდეგ, რაც თითოეული აქტივის არსებობა და გადაცემის გზა დადასტურდება. <a href="/ka/blog/production-handover-checklist-for-a-nontechnical-founder">Production handover-ის პრაქტიკული სია</a> დაგეხმარებათ მიღებული სისტემის ყოველდღიური მართვის დასაგეგმად; აქ გადაწყვეტილება ჯერ აქტივის შეძენას ეხება.</p>

<h2 id="scope-boundary">საჯარო მტკიცებულებიდან ავტორიზებულ შემოწმებამდე</h2>
<p>საჯარო review შემოიფარგლება იმით, რასაც რიგითი ვიზიტორი იღებს: გვერდებით, საჯაროდ ჩამოტვირთვადი ფაილებით, response header-ებითა და გამოქვეყნებული ფუნქციებით. ასეთი შემოწმება არ იძლევა უფლებას პაროლის გამოცნობაზე, სხვის მონაცემზე წვდომის მცდელობაზე ან ცოცხალ გარემოში დესტრუქციულ ტესტზე. იგი ვერ ადგენს კერძო რეპოზიტორიის წესებსა და სერვერის შიდა ლოგიკას. vibeCODING-ის ღრმა შემოწმება მხოლოდ წვდომისა და test boundary-ის შეთანხმების შემდეგ განისაზღვრება.</p>
<p><a href="https://owasp.org/www-project-top-ten/">OWASP-ის ვებრისკების სია</a> გავრცელებული ვებრისკების სახელებსა და კონტექსტს აძლევს გუნდს, მაგრამ სიის პუნქტის არსებობა კონკრეტულ აპში დაუდასტურებელ სისუსტეს არ ნიშნავს. მყიდველს სჭირდება მტკიცებულებით აღწერილი პრობლემა, შესაძლო გავლენა, გამოსწორების მფლობელი და ხელახალი ტესტი. ამიტომ ავტომატური გაფრთხილება გამოიყენეთ შეკითხვის დასასმელად და არა გარიგების შეჩერების ავტომატურ საფუძვლად.</p>
<p>თუ გამყიდველი რეპოზიტორიასა და production ანგარიშს მხოლოდ გარიგების გვიან ეტაპზე ხსნის, ეს ხელმისაწვდომობის შეზღუდვა რეესტრში ცალკე ჩაწერეთ. მყიდველს შეუძლია მოითხოვოს კონკრეტული დოკუმენტის ჩვენება, უსაფრთხო read-only სესია ან სპეციალისტის მონაწილეობა. წვდომის არქონა ვარაუდით არ შეავსოთ: იგი არც წესრიგს და არც დარღვევას არ ამტკიცებს.</p>

<h2 id="deal-matrix">აღმოჩენიდან გარიგების პირობამდე</h2>
<p>ყოველი რისკი აქციეთ მოქმედებად, რომლის მფლობელი და შემოწმების პირობა ცნობილია. ტექნიკური შეფასება მყიდველისთვის ღირებულია მაშინ, როცა შეუძლია გაურკვევლობას მართვადი ადგილი მიუჩინოს. ქვემოთ მოცემული მატრიცა მაგალითია; ის არ ადგენს ფასს, სამართლებრივ ვალდებულებას ან უნივერსალურ მისაღებ რისკს.</p>
