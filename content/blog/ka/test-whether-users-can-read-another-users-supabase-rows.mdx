<p><strong>პირდაპირი პასუხი:</strong> BOLA ან IDOR მაშინ ჩნდება, როცა სერვერი მიღებულ ობიექტის იდენტიფიკატორს იღებს, მაგრამ არ ამოწმებს, ეკუთვნის თუ არა ჩანაწერი მოქმედ მომხმარებელს ან მის tenant-ს. შემოწმებისთვის გამოიყენეთ ორი კონტროლირებადი ანგარიში, ცალკე სატესტო ჩანაწერები და ყველა შესაბამისი API გზა. საჯარო აპლიკაციის review მხოლოდ ჩამოსატვირთ ზედაპირს აჩვენებს; ავტორიზებული ტესტის საზღვრის შესათანხმებლად <a href="/contact">მოითხოვეთ vibecoding.ge-ს scoped review</a>.</p>

<h2 id="meaning">რას ნიშნავს BOLA ან IDOR AI-ით აწყობილ აპში?</h2>

<p>BOLA, ანუ Broken Object Level Authorization, აღწერს ობიექტის დონეზე ავტორიზაციის ჩავარდნას. ძველი სახელწოდება IDOR, Insecure Direct Object Reference, იმავე ტიპის პრობლემას ეხება: მომხმარებელი აგზავნის სხვა ჩანაწერის ID-ს, ხოლო API პასუხს აბრუნებს მხოლოდ იმიტომ, რომ მოთხოვნა ფორმალურად სწორია. OWASP API Security-ის <a href="https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/">API1:2023</a> სწორედ ამ საზღვარს გამოყოფს API-ის მთავარ რისკად.</p>

<p>ეს პრობლემა მხოლოდ Supabase-ს არ ეკუთვნის. იგივე ხდება REST endpoint-ში, GraphQL query-ში, server action-ში, ფაილის ჩამოტვირთვის გზაზე ან background ფუნქციაში. შემთხვევითი ან გრძელი ID-ის გამოყენება გამოცნობას ართულებს, მაგრამ საკუთრებას არ ამტკიცებს. ავტორიზაციამ უნდა შეადაროს მოქმედი ანგარიშის იდენტობა მოთხოვნილ ობიექტთან, tenant-თან ან წინასწარ დაშვებულ ბიზნეს-ურთიერთობასთან.</p>

<p>Supabase-ის <a href="https://supabase.com/docs/guides/database/postgres/row-level-security">Row Level Security დოკუმენტაცია</a> აჩვენებს, როგორ გამოიყენება `auth.uid()` მომხმარებლის კონტექსტის შესადარებლად. PostgreSQL-ის <a href="https://www.postgresql.org/docs/17/ddl-rowsecurity.html">row security წესები</a> ცალ-ცალკე მართავს ხილვადობას და დასაშვებ ახალ მდგომარეობას. ამიტომ მხოლოდ `SELECT` შემოწმება არ კმარა, თუ აპს `UPDATE`, `DELETE` ან ექსპორტის გზა აქვს.</p>

<h2 id="test-scope">tenant isolation-ის შემოწმების არეალი</h2>

<p>შემოწმების ობიექტი უნდა იყოს ბიზნეს-მოქმედება და არა მხოლოდ ერთი გვერდი. ერთი ინვოისი შეიძლება გამოჩნდეს UI-ში, API პასუხში, PDF ჩამოტვირთვაში, ძიებაში ან ადმინისტრატორის ექსპორტში. წინასწარ ჩამოწერეთ თითოეული გზა და მოსალოდნელი შედეგი.</p>

  <li><strong>შეამოწმეთ ანგარიშის B უკუ-მიმართულება.</strong> სიმეტრიული ტესტი აჩვენებს, ხომ არ მუშაობს შემთხვევით მხოლოდ ერთი tenantთვის. ნეგატიური შედეგი ორივე მიმართულებით ცალკე ჩაიწერეთ.</li>
  <li><strong>გაარჩიეთ საჯარო და ავტორიზებული მტკიცებულება.</strong> ჩამოტვირთული JavaScript bundle ან საჯარო API დოკუმენტი შეიძლება მხოლოდ ზედაპირის მინიშნება იყოს. პირადი ჩანაწერის ტესტი იწყება მაშინ, როცა owner-თან წვდომა და არადესტრუქციული საზღვარი შეთანხმებულია.</li>

<h2 id="limitations">რა ვერ დადასტურდება საჯარო review-ით?</h2>

<p>საჯარო ფაილების scan ამოწმებს მხოლოდ იმას, რასაც ჩვეულებრივი სტუმარი ჩამოტვირთავს. იგი ვერ ამტკიცებს private database policy-ს, server-side authorization-ს, ყველა hidden route-ს ან tenant რეალურ იზოლაციას. ასეთი დასკვნისთვის საჭიროა შეთანხმებული წვდომა, სატესტო ანგარიში და არადესტრუქციული მოქმედებების სია.</p>

<p>ასევე არ უნდა აურიოთ პოტენციური IDOR და დადასტურებული გავლენა. თუ bundle-ში ჩანს `id` პარამეტრი, ეს მხოლოდ შემოწმების ჰიპოთეზაა. საბოლოო ანგარიშში თითოეული აღმოჩენა უნდა იყოს მიბმული request-ზე, response-ზე, ობიექტის მფლობელზე და იმაზე, შეიცვალა თუ არა მდგომარეობა. vibecoding.ge-ს scoped review არსებულ AI-ით აწყობილ აპს ამოწმებს, ადგენს დადასტურებული მიგნებების პრიორიტეტს და repair/rescan-ის შემდეგ handover-ს აფიქსირებს. იგი ახალ აპს არ აშენებს და უსაფრთხოების სერტიფიკაციას არ გპირდებათ.</p>

<h2 id="release-decision">როდის არის შედეგი საკმარისი release გადაწყვეტილებისთვის?</h2>

<p>release-მდე საკმარისი მინიმუმია არა ერთი მწვანე ეკრანი, არამედ განმეორებადი მტკიცებულების ნაკრები: ყველა რეალური ობიექტის გზა ინვენტარშია, ჩვეულებრივი user-ის დადებითი და უარყოფითი ტესტები ჩაწერილია, უარის პასუხი მონაცემს არ აბრუნებს, repair-ის შემდეგ იგივე test card ხელახლა შესრულდა და დარჩენილ უცნობებს ჰყავთ პასუხისმგებელი.</p>

<p>თუ რომელიმე გზა ჯერ ვერ მოწმდება, მას „დაცულად“ ნუ მონიშნავთ. ჩაწერეთ საჭირო წვდომა, ტესტის ფარგლები და შემდეგი ნაბიჯი. ასეთი ჩანაწერი უკეთეს release გადაწყვეტილებას იძლევა, ვიდრე ზოგადი დასკვნა, რომელიც მხოლოდ front-end-ის ქცევას აღწერს.</p>

<h2 id="faq">ხშირად დასმული კითხვები</h2>
