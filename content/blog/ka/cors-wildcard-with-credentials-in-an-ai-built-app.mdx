<h2 id="cors-boundary">CORS და ბრაუზერის საზღვარი API-სთან</h2>
<p>Cross-Origin Resource Sharing, ანუ CORS, ბრაუზერის წესია. ის განსაზღვრავს, რომელი სხვა origin-ის გვერდს შეუძლია პასუხის წაკითხვა, როცა კლიენტი თქვენს API-ს მიმართავს. <a href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS">MDN განმარტავს</a>, რომ სერვერი response-ში აგზავნის ნებადართულ origin-ს და საჭიროების შემთხვევაში სხვა CORS header-ებსაც. ეს შეთანხმება მოქმედებს ბრაუზერის წაკითხვის წესზე; ის თავისით არ ქმნის ავტორიზაციას.</p>
<p>AI builder-ის მიერ აწყობილ აპში ერთი უნივერსალური middleware შეიძლება ყველა route-ს ერთნაირ header-ს უმატებდეს. ეს მოსახერხებელია დემოსთვის, მაგრამ ბიზნეს-მონაცემების მქონე route-ზე ზედმეტად ფართო პასუხს ქმნის. CORS-ის შემოწმებისას აღწერეთ, რომელ origin-ს სჭირდება წვდომა, რომელი route აბრუნებს მგრძნობიარე მონაცემს და როგორ გადაეცემა სესია. შემდეგ შეადარეთ მოთხოვნა რეალურ response-ს.</p>

Origin-ის შედარება მკაფიო უნდა იყოს და კოდმა უცნობი მნიშვნელობა ნაგულისხმევად არ უნდა დაუშვას. <a href="https://web.dev/articles/cross-origin-resource-sharing">web.dev-ის CORS სახელმძღვანელო</a> credentialed მოთხოვნისთვის explicit origin-ის დაბრუნების მაგალითს აღწერს.</p>

<h2 id="response-test">დაცული route-ის ტესტის თანმიმდევრობა</h2>
<p>ტესტი შეასრულეთ მხოლოდ შეთანხმებულ staging გარემოში ან ავტორიზებულ ანგარიშზე. მიზანია დაინახოთ განსხვავება origin-ის პოლიტიკასა და სერვერის უფლებებს შორის. თითოეული ცდა ჩაიწერეთ ისე, რომ მგრძნობიარე cookie, token და მონაცემი ანგარიშში სრულად არ მოხვდეს.</p>
<ol>
  <li><strong>პირველი ნაბიჯი: აირჩიეთ route:</strong> დაასახელეთ ერთი მოთხოვნა, რომელიც ანგარიშის, შეკვეთის ან ორგანიზაციის მონაცემს აბრუნებს. ჩაწერეთ user role, method და მოსალოდნელი პასუხი.</li>
  <li><strong>მეორე ნაბიჯი: შეცვალეთ origin:</strong> უსაფრთხო ტესტის client-იდან გამოიყენეთ ნებადართული origin, შემდეგ უცნობი origin. შეადარეთ <code>Access-Control-Allow-Origin</code>, <code>Access-Control-Allow-Credentials</code> და response-ის წაკითხვა.</li>
  <li><strong>მესამე ნაბიჯი: შეამოწმეთ preflight:</strong> გაგზავნეთ <code>OPTIONS</code> მოთხოვნა იმ მეთოდითა და header-ით, რომელსაც კლიენტი რეალურად იყენებს. უცნობი origin ან ზედმეტი header ნებადართულ სიაში არ უნდა მოხვდეს.</li>
  <li><strong>მეოთხე ნაბიჯი: გადაამოწმეთ შედეგი:</strong> კონტროლის პასუხი შეიძლება იყოს, მაგალითად, 200 ან 403, მაგრამ საბოლოო მტკიცებულება მონაცემის წაკითხვა და route-ის ქცევაა. თუ header არასათანადოა, მაგრამ სერვერი მაინც აბრუნებს სხვის მონაცემს, პრობლემა CORS-ზე ფართოა.</li>
</ol>
<p>ტესტის დადებითი და უარყოფითი შემთხვევა ცალკე შეინახეთ. „ნებადართულმა origin-მა მიიღო პასუხი“ და „უცნობმა origin-მა ვერ წაიკითხა პასუხი“ ორი სხვადასხვა დასკვნაა. ერთი წარმატებული request მთელ აპს ვერ წარმოადგენს. შეამოწმეთ ერთი კრიტიკული route და შემდეგ იგივე policy-ის სხვა გამოყენებები, თუ middleware საერთო ჩანს.</p>

<h2 id="cors-auth">CORS და API authorization</h2>
<p>თუ თავდამსხმელი საკუთარი სერვერიდან პირდაპირ აგზავნის მოთხოვნას, CORS-ის ბრაუზერული წესი მის სერვერს არ აჩერებს. ამიტომ API-მ თავად უნდა შეამოწმოს session, token, როლი და კონკრეტულ ობიექტზე მფლობელობა. CORS მხოლოდ ბრაუზერს ეუბნება, რომელი გვერდი შეძლებს პასუხის წაკითხვას. ეს განსხვავება განსაკუთრებით მნიშვნელოვანია მაშინ, როცა აპს ერთზე მეტი კლიენტი ან მობილური გამოყენება აქვს.</p>
<p><a href="https://owasp.org/API-Security/editions/2023/en/0x11-t10/">OWASP API Security Top 10</a> API authorization-სა და resource access კონტროლებს CORS-ისგან ცალკე განიხილავს. ამიტომ review ცხრილში ორი სვეტი შეინარჩუნეთ: „ბრაუზერის წაკითხვის პოლიტიკა“ და „სერვერის უფლებების შემოწმება“. ერთი მწვანე პასუხი მეორეს არ ანაცვლებს.</p>

<h2 id="repair-evidence">გამოსწორების მტკიცებულება</h2>
<p>შესწორების დაწყებამდე შეინახეთ საწყისი response, მოთხოვნის origin, გამოყენებული client და route. ცვლილების შემდეგ იგივე სცენარი გაიმეორეთ იგივე ანგარიშითა და გარემოთი. ჩაიწერეთ, რომ ნებადართული origin ისევ მუშაობს, უცნობი origin პასუხს ვერ კითხულობს და server-side authorization უცვლელად მოქმედებს.</p>
<p>განსაკუთრებული ყურადღება მიაქციეთ cache-ს. თუ response origin-ით იცვლება, proxy-სა და CDN-ს შეიძლება <code>Vary: Origin</code> სჭირდებოდეს, რათა ერთი origin-ის პასუხი მეორეს არ გადაეცეს. ეს დასკვნა უნდა დაეყრდნოს თქვენს არქიტექტურას და არა framework-ის ვარაუდს. ასევე შეამოწმეთ credentials-ის რეალური გადაცემა: header-ის სახელის ნახვა არ ნიშნავს, რომ სესია სწორად ან უსაფრთხოდ მუშავდება.</p>
<p>დასკვნაში გამოიყენეთ სამი დონე: დადასტურებული, სავარაუდო და მიუწვდომელი. დადასტურებულად ჩათვალეთ კონკრეტულ route-ზე ნანახი response და მონაცემის ქცევა. სავარაუდოა ის, რაც საერთო middleware-იდან ჩანს, მაგრამ ყველა route-ზე არ გაგიმეორებიათ. მიუწვდომელია private API, სხვა კლიენტი, კოდის ისტორია ან deployment-ის ფენა, რომელზეც წვდომა არ გქონდათ.</p>

<h2 id="limitations">საჯარო CORS შემოწმების შეზღუდვები</h2>
<p>საჯარო გვერდიდან ნანახი header ვერ ამტკიცებს ყველა API route-ის, ყველა role-ის, private proxy-სა და კოდის უსაფრთხოებას. ბრაუზერის მიერ response-ის დაბლოკვა ვერ ამბობს, რომ მონაცემი სერვერზე საერთოდ არ გაიგზავნა. ასევე, CORS ვერ აფასებს XSS-ს, CSRF-ს, session theft-ს, IDOR-ს ან ბიზნეს-ლოგიკის ყველა ხარვეზს. <a href="/ka/blog/csp-da-nonce-aiit-shekmnil-apshi">საჯარო და authenticated review-ის განსხვავება</a> ცალკე უნდა ჩაიწეროს.</p>
<p>მომხმარებლისთვის უსაფრთხო გადაწყვეტილება არის ზუსტად დასახელებული scope: რომელი origin, route, role, მეთოდი და response შემოწმდა. ყველაფერი დანარჩენი ღია საკითხად დატოვეთ, სანამ შესაბამისი მტკიცებულება არ გექნებათ.</p>

<h2 id="faq">ხშირად დასმული კითხვები</h2>
<h3 id="faq-1">CORS-ის wildcard ყოველთვის დაუცველია?</h3>
<p>არა. სრულად საჯარო, არაავტორიზებული რესურსისთვის wildcard შეიძლება მიზანმიმართული იყოს. რისკი ჩნდება მაშინ, როცა ფართო policy ავტორიზებულ ან მგრძნობიარე response-ს ეხება და origin-ის მკაფიო კონტროლი არ არსებობს.</p>
<h3 id="faq-2">თუ ბრაუზერი credentialed response-ს ბლოკავს, პრობლემა დასრულებულია?</h3>
<p>არა. ეს მხოლოდ ბრაუზერის წაკითხვის წესს აჩვენებს. API-მ მაინც უნდა შეამოწმოს სესია, როლი და ობიექტზე უფლება, ხოლო სხვა client-ები ცალკე უნდა შეფასდეს.</p>
<h3 id="faq-3">რა უნდა გავუგზავნო review-ის მოთხოვნასთან ერთად?</h3>
<p>მიუთითეთ საჯარო URL, ნებადართული origin-ები, test role-ები, სასურველი გარემო და კრიტიკული route-ები. კერძო წვდომა ან რეალური მომხმარებლის მონაცემი წინასწარი შეთანხმების გარეშე არ არის საჭირო.</p>
