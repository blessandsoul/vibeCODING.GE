<h2 id="ssrf-boundary">რას ნიშნავს SSRF URL ფუნქციისთვის?</h2>
<p>Server-Side Request Forgery, ანუ SSRF, არის შემთხვევა, როცა აპის სერვერი მომხმარებლის გავლენით თვითონ აკეთებს ქსელურ მოთხოვნას. მფლობელი შეიძლება URL-ს იყენებდეს სურათის preview-სთვის, დოკუმენტის import-ისთვის, webhook შემოწმებისთვის ან მესამე მხარის API-ს დასაკავშირებლად. თუ საბოლოო დანიშნულება და გამოყენებული protocol მკაფიოდ არ არის შეზღუდული, server შეიძლება გახდეს proxy იმ მიმართულებისთვის, რომლის ნახვაც მომხმარებელს არ უნდა შეეძლოს.</p>
<p><a href="https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html">OWASP SSRF Prevention Cheat Sheet</a> განასხვავებს შემთხვევას, როცა აპმა მხოლოდ წინასწარ ცნობილ სერვისებს უნდა მიმართოს, იმ შემთხვევისგან, როცა ნებისმიერი გარე მისამართი ბიზნესის ფუნქციის ნაწილია. ეს განსხვავება review პირველ გადაწყვეტილებად აქციეთ. allowlist მქონე ფუნქცია და თავისუფალი URL proxy ერთნაირი რისკითა და კონტროლით არ ფასდება.</p>

<ul>

  <li>ბმულის წინასწარი ჩვენება, ეკრანის სურათი და მეტამონაცემების ამოღება;</li>
  <li>ადმინისტრაციული ხელსაწყო, რომელიც მომხმარებლის მითითებულ endpoint-ს ამოწმებს;</li>

<h2 id="safe-fetch-sequence">უსაფრთხო fetch თანმიმდევრობა</h2>
<p>უსაფრთხო იმპლემენტაციის playbook ერთ კონტროლზე არ ჩერდება. თითოეული ნაბიჯი ცალკე მტკიცებულებად ჩაიწეროს:</p>
<ol>
  <li><strong>შეამოწმეთ ფორმატი:</strong> გამოიყენეთ ერთი URL parser და უარყავით parser disagreement, უცნობი scheme და დაუშვებელი port.</li>
  <li><strong>მიაბით დანიშნულებას:</strong> allowlist-ს შეადარეთ canonical host და შესაბამისი IP-ები, როცა ფუნქცია ცნობილ სერვისებს ეხება.</li>
  <li><strong>გააკონტროლეთ redirect:</strong> redirect ავტომატურად არ მიჰყვეს client-მა, ან ყოველი ახალი დანიშნულება თავიდან გაიაროს იგივე წესები.</li>
  <li><strong>შეამოწმეთ DNS დროითი ცვლილება:</strong> hostname შემოწმება და საბოლოო connection მისამართი ერთსა და იმავე დაცვას უნდა დაექვემდებაროს.</li>
  <li><strong>შეზღუდეთ protocol და response:</strong> გამოიყენეთ საჭირო scheme, timeout, ზომა და content type. raw response არ გადასცეთ პირდაპირ მომხმარებელს.</li>
  <li><strong>გაყავით ქსელური უფლებები:</strong> fetch worker-ს არ უნდა ჰქონდეს იმაზე მეტი შიდა წვდომა, ვიდრე ფუნქციას სჭირდება.</li>
</ol>
<p>ეს ნაბიჯები არ არის კონკრეტული framework მზა კონფიგურაცია. მათი მიზანია review-ისთვის შემოწმებადი კრიტერიუმების შექმნა. საბოლოო implementation დამოკიდებულია hosting-ზე, network policy-ზე და გამოყენებულ ბიბლიოთეკებზე.</p>
